# UX AUDIT REPORT
## Advay Learning — "Learn With Your Whole Body" Kids Educational Platform

**Date:** 2026-03-15
**Auditor:** Claude (UX Research & Product Audit)
**Scope:** Full user journey from landing to gameplay

---

## 1. PRODUCT VISION UNDERSTANDING

### What the app appears to be trying to achieve
**Advay Learning** is a computer-vision-powered educational platform for children (ages 2-8) where kids learn by moving their whole bodies. The core differentiator is hand/pose/face/voice tracking — children "draw letters in the air," "do yoga poses," "count with fingers," rather than just tapping screens.

### Primary Users
1. **Children (2-8 years)**: The primary players — low reading comprehension, high visual dependence, need immediate gratification, low frustration tolerance
2. **Parents**: The account creators, profile managers, progress monitors — need trust, clarity, and efficiency
3. **Teachers/Classrooms**: (Implied) Potential group usage scenario

### Core Usage Loop (Intended)
```
Landing Page → Register/Login (parent) → Dashboard → Browse Games → Select Game → Camera Permission → Play → Celebrate → Return to Games
```

### UX Principles that SHOULD logically follow from this vision
1. **Immediacy**: Child should get from "I want that game" to playing in ONE tap
2. **Movement-first**: Camera enablement should feel exciting, not bureaucratic
3. **Low text, high visual**: Kids can't read complex instructions
4. **Parent-setup-once, child-play-forever**: Registration and setup should be one-time friction
5. **Consistent patterns**: Every game should start, pause, end the same way
6. **Celebration over correction**: Positive feedback, rapid momentum

### Vision Gaps and Contradictions Found

| Aspect | Stated Vision | Current Implementation | Gap |
|--------|---------------|----------------------|-----|
| **Immediacy** | "Learn with your whole body" | Many games require 2-3 clicks before playing | Game cards promise "Jump In!" but deliver "Choose difficulty" |
| **Child-first** | Ages 2-8, playful | Camera permission screens are adult-wordy | "We need camera access to see your hand movements" is too adult |
| **Consistent patterns** | All 250+ games | 60+ games, each with custom start screens | No unified pre-game or completion pattern |
| **Low friction** | "Instantly available" | Onboarding + camera setup + per-game menus | Multiple steps before value |

---

## 2. UX AUDIT ASSUMPTIONS

1. **Children do NOT read carefully** — They recognize icons, colors, and patterns
2. **Parents are time-poor** — They want setup to be fast and then get out of the way
3. **Every extra click = lost engagement** — Kids will abandon if gameplay doesn't start quickly
4. **Camera is magical, not scary** — The CV features should feel like a superpower, not a permission form
5. **Momentum matters more than structure** — Smooth flow beats organized multi-step forms
6. **Child's intent is "play NOW"** — Anything between card-click and gameplay is friction

## 3. UX ISSUE REGISTER

### ISSUE #001: Game Card "Play" Buttons Don't Immediately Play

| Attribute | Value |
|-----------|-------|
| **Severity** | High |
| **UX Category** | label mismatch, flow friction |
| **User Scenario** | Child sees a fun game card and wants to play it NOW |
| **Current Flow** | 1. Child sees game card with "Jump In!" button → 2. Clicks button → 3. Arrives at game page → 4. Shown pre-game menu with difficulty selection → 5. Must click "Start" to actually play |
| **Why This Is Poor UX** | - Button promises "Jump In!" but delivers "Choose a setting" <br> - Child intent is "play" not "configure" <br> - Adds friction between desire and reward <br> - Breaks immediacy expectation |
| **Why Especially Bad for Kids App** | - Kids don't understand why they clicked "play" but aren't playing <br> - May lose interest during setup <br> - Creates confusion about what buttons do |
| **Evidence** | `src/frontend/src/components/GameCard.tsx` (line 75: `buttonText = 'Play Game'`) <br> `src/frontend/src/pages/SimpleAddition.tsx` (lines 227-256: custom pre-game menu) <br> `src/frontend/src/pages/AlphabetGame.tsx` (lines 824-846: PreGameMenu component) |
| **Recommendation** | Default mode should launch immediately. Options move inside game. |
| **Better Label Copy** | If menu IS required: "Choose Mode" <br> If immediate play: Keep "Play" or "Jump In!" |
| **Better Flow Proposal** | 1. Click card → 2. Game starts immediately with default (easy) mode <br> 3. Mode/difficulty selector lives in pause menu or as on-screen toggle <br> 4. Remember last-used mode per game |
| **Implementation** | Move into play area, progressive disclosure |
| **Effort** | M |
| **Acceptance Criteria** | Clicking a game card gets child to gameplay in <2 seconds |

### ISSUE #002: Camera Permission Happens Too Late

| Attribute | Value |
|-----------|-------|
| **Severity** | Critical |
| **UX Category** | flow friction, vision misalignment |
| **User Scenario** | Child selects game, gets excited, THEN is asked for camera permission |
| **Current Flow** | 1. Click game card → 2. Load game page → 3. MAYBE see onboarding → 4. Camera permission prompt during game load → 5. If denied, show "continue with mouse" fallback |
| **Why This Is Poor UX** | - Permission interrupts the "moment of play" <br> - Camera is the CORE feature of this platform — hiding it until mid-flow is bizarre <br> - Fallback mode makes it feel optional rather than magical |
| **Why Especially Bad for Kids App** | - Child doesn't understand "camera permission" <br> - Interruption kills excitement <br> - Makes the core differentiator feel like bureaucracy |
| **Evidence** | `src/frontend/src/components/OnboardingFlow.tsx` (lines 12-14: camera is step 2 of onboarding) <br> `src/frontend/src/components/routing/CameraSafeRoute.tsx` (camera error handling) <br> `src/frontend/src/pages/AlphabetGame.tsx` (lines 146-154: camera permission state) |
| **Recommendation** | Camera setup should happen ONE TIME during parent registration/first visit, celebrated as a "superpower," not as a per-game permission |
| **Better Flow Proposal** | **PARENT SETUP FLOW:** <br> 1. During registration: "Let's set up the magic camera!" <br> 2. One-time camera enablement with celebration <br> 3. Store permission state <br> **CHILD FLOW:** <br> 4. All games assume camera is ready (or fall back gracefully) |
| **Implementation** | Move camera setup to registration/onboarding flow |
| **Effort** | L |
| **Acceptance Criteria** | Camera permission requested once, not per-game. Treated as "enabling magic" not "granting access" |

### ISSUE #003: Registration Flow Asks Parent + Child Info Simultaneously

| Attribute | Value |
|-----------|-------|
| **Severity** | High |
| **UX Category** | cognitive load, flow friction |
| **User Scenario** | Parent trying to quickly set up account for eager child |
| **Current Flow** | 1. Parent enters email/password <br> 2. SAME form: parent must enter child name, age, language <br> 3. Click "Create Account" <br> 4. Redirected to login page (??!) <br> 5. Must then log in <br> 6. THEN can access games |
| **Why This Is Poor UX** | - Mixes two different user intents (account setup vs profile setup) <br> - Parent may not know child's language preference yet <br> - Redirect to login after registration is confusing <br> - Parent info is for security, child info is for learning — different mental models |
| **Why Especially Bad for Kids App** | - Child is waiting (often impatiently) during setup <br> - Longer form = more abandonment <br> - Parent creates "placeholder" child profile just to get through it |
| **Evidence** | `src/frontend/src/pages/Register.tsx` (lines 158-310: combined parent + child form) <br> Lines 76-77: Register → redirect to login |
| **Recommendation** | Split into two phases: Account creation (security focus) then Dashboard welcome (child focus) |
| **Better Flow Proposal** | **PHASE 1: Account** <br> 1. Email + password only <br> 2. Create → Auto-login → Welcome to parent dashboard <br> **PHASE 2: First Child Profile** <br> 3. Dashboard prompts: "Let's add your first learner!" <br> 4. Child name, age, language in a focused, celebratory flow <br> 5. Immediately go to games (no detour through login) |
| **Implementation** | Split registration into account + profile steps |
| **Effort** | M |
| **Acceptance Criteria** | Parent can create account in <30 seconds. Child profile added after, separately. No login redirect required. |

### ISSUE #005: No Clear "Back to Games" After Game Completion

| Attribute | Value |
|-----------|-------|
| **Severity** | Medium |
| **UX Category** | recovery/momentum, navigation |
| **User Scenario** | Child finishes a game, wants to play another |
| **Current Flow** | Varies by game! Some have "Exit", some "Play Again", some navigate to different places |
| **Why This Is Poor UX** | - Inconsistent exit patterns <br> - "Exit" sounds scary (like quitting) <br> - No clear path to next game |
| **Why Especially Bad for Kids App** | - Child may accidentally leave game flow <br> - "Exit" = punishment connotation <br> - Breaks momentum between games |
| **Evidence** | `src/frontend/src/pages/SimpleAddition.tsx` (lines 396-409: custom completion UI with "Exit" button) <br> `docs/GAME_UI_COMPONENT_REFACTOR.md` (acknowledges inconsistent completion screens) |
| **Recommendation** | Standardize completion screen with "Play Again" (primary) and "More Games" (secondary) |
| **Better Label Copy** | - Primary: "Play Again" <br> - Secondary: "See More Games" (NOT "Exit") |
| **Better Flow Proposal** | All games use shared `GameResultScreen` component: <br> 1. Show score/celebration <br> 2. "Play Again" (same game, different content) <br> 3. "More Games" → back to /games |
| **Implementation** | Use GameResultScreen component (already designed, per refactor doc) |
| **Effort** | L (requires migrating all games) |
| **Acceptance Criteria** | All 60+ games use identical completion screen with consistent actions |

### ISSUE #008: In-Game Pause/Exit Flow Requires Parent Gate Every Time

| Attribute | Value |
|-----------|-------|
| **Severity** | Medium |
| **UX Category** | flow friction, kids-app expectation failure |
| **User Scenario** | Child wants to pause game or switch games |
| **Current Flow** | 1. Child clicks pause/exit <br> 2. Some games show confirmation, some require parent gate <br> 3. If parent gate, child stuck waiting <br> 4. Inconsistent across games |

| **Implementation** | Review and update ParentGate usage |
| **Effort** | M |
| **Acceptance Criteria** | Child can pause and exit any game without parent intervention |

## 4. TOP UX PRINCIPLES THE APP IS CURRENTLY VIOLATING

1. **Too many steps before play** — Game cards should lead to gameplay, not configuration menus

2. **Mismatch between CTA and outcome** — "Play" buttons that open setup screens break trust

3. **Too much pre-play setup** — Difficulty selection, mode selection should be in-game, not pre-game

4. **Inconsistent start patterns** — 60+ games, each with unique entry flow

5. **Generic app UX where game UX is needed** — Subscription cards, pending badges, "exit" buttons feel like SaaS, not kids games

6. **Unclear product vision in flows** — Can't tell if this is for parents (account setup) or kids (games), shifts abruptly between modes

|----------|-----|--------|--------|-----|

## 6. STRUCTURAL UX PROBLEMS

1. **No unified pre-game or post-game pattern** — The app recognizes this (see `GAME_UI_COMPONENT_REFACTOR.md`) but hasn't implemented the solution. 60+ games have custom menus.

2. **Child vs parent modes not separated** — Dashboard mixes concerns. Scary "failed" badges visible to kids.

3. **Setup happens at wrong time** — Camera permission asked mid-flow. Registration asks for everything at once.

4. **Navigation creates "traps"** — Exit buttons that behave differently across games. Inconsistent back navigation.

5. **Core differentiator (CV) feels bureaucratic** — Hand/pose tracking is the magic, but permission flows make it feel like compliance.

---

## 7. IDEAL TARGET PATTERN

### For This Product Specifically:

1. **From card to gameplay in one tap** — Game card → gameplay (default mode). No intermediate menus.

2. **Default mode launches instantly** — Easy/medium/learn mode defaults per age. Advanced options in pause menu.

3. **Advanced options live inside play area** — Mode selection, difficulty, hints available during play, not before.

4. **CTA labels exactly match outcome** — "Play" → play. "Choose Mode" → mode picker. "See More Games" → games list.

5. **Replay/restart is immediate** — "Play Again" button instantly restarts with new content.

6. **Child-facing flows have minimal text and minimal branching** — Icons, patterns, sounds over words.

7. **Camera = Magic, not Permission** — One-time "Enable Magic" celebrated as superpower, not per-game permission form.

8. **Parent setup happens once, then gets out of the way** — Account creation → profile creation → games. No repeated detours.

## 9. SUMMARY

**Product Promise:** "Learn With Your Whole Body" — magical, movement-based learning for kids

**Current Reality:** A well-intentioned app that **feels more like a generic web app with games bolted on** than a unified magical experience. The computer vision features are undersold, the flows are fragmented, and too many steps stand between "I want to play" and actually playing.

**Core Insight:** This app's unique value proposition (hand/pose tracking, full-body learning) is treated as a technical implementation detail rather than a celebrated feature. The camera permission flows, tutorial systems, and inconsistent game entry patterns all work *against* the sense of magic and immediacy that a kids learning app should deliver.

**The Fix:** Re-center on the child's experience: one tap from discovery to delight. Move configuration, mode selection, and setup OUT of the path between seeing and playing. Celebrate the camera as a superpower, not a permission. Make every game start, pause, and end the same way.
